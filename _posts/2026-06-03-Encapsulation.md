객체지향 프로그래밍(Object-Oriented Programming)의 4대 특징으로는 추상화(Abstraction), 캡슐화(Encapsulation), 상속(Inheritance), 다형성(Polymorphism)이 있다. 이 중 캡슐화는 객체지향 설계의 가장 기본이 되는 개념으로, 유지보수하기 쉽고 안정적인 프로그램을 만들기 위해 반드시 이해해야 하는 원칙이다.

많은 개발자들이 캡슐화를 "데이터를 숨기는 것"이라고만 기억한다. 물론 틀린 설명은 아니지만 캡슐화의 진짜 목적은 단순히 데이터를 감추는 것이 아니다. 객체가 자신의 상태를 스스로 관리하고 보호할 수 있도록 만드는 것이 핵심이다. 즉, 외부에서 객체 내부의 데이터를 마음대로 변경하지 못하게 하고, 객체가 허용한 방식으로만 상태를 변경할 수 있도록 만드는 것이 캡슐화의 본질이라고 할 수 있다.

예를 들어 은행 계좌(BankAccount)를 생각해보자. 계좌에는 잔액(balance)이라는 중요한 데이터가 존재한다. 만약 잔액을 누구나 자유롭게 변경할 수 있다면 어떤 문제가 발생할까?
``` java
account.balance = -1000000; 
```


이처럼 외부에서 직접 접근할 수 있다면 음수 잔액이 저장될 수도 있고, 비즈니스 규칙이 무너질 수도 있다. 결국 객체는 자신의 상태를 보호하지 못하게 된다.

그래서 객체지향 프로그래밍에서는 중요한 데이터를 외부에서 직접 접근하지 못하도록 private으로 숨긴다.

``` java
private int balance; 
```


이제 외부에서는 balance 변수에 직접 접근할 수 없다. 하지만 데이터를 완전히 숨겨버리면 조회나 변경도 불가능하기 때문에 객체가 제공하는 메서드를 통해서만 접근하도록 만든다.
``` java
public int getBalance() {
     return balance; } 
```
``` java
public void deposit(int amount) {
     balance += amount; } 
```

이처럼 객체는 자신의 상태를 직접 노출하는 대신, 정해진 메서드를 통해서만 접근을 허용한다. 이것이 캡슐화의 핵심이다.

캡슐화가 중요한 이유는 객체의 무결성(Integrity)을 보장할 수 있기 때문이다. 객체는 특정한 규칙을 가지고 동작해야 한다. 예를 들어 은행 계좌는 음수 금액을 입금할 수 없어야 하고, 회원 정보는 이름이 비어 있을 수 없어야 한다. 만약 필드를 public으로 공개해 버리면 이러한 규칙을 강제할 수 없게 된다.

반면 캡슐화를 적용하면 데이터를 변경하는 과정에서 검증 로직을 추가할 수 있다.
``` java
public void deposit(int amount) {
      if(amount <= 0) {
         throw new IllegalArgumentException(); 
    }
      balance += amount;
 } 
```


이제 잘못된 값은 객체 내부에서 차단할 수 있다. 즉, 객체는 자신의 상태를 스스로 보호하게 된다.

캡슐화는 Getter와 Setter와도 깊은 관련이 있다. 많은 초보 개발자들이 필드를 private으로 선언한 뒤 모든 필드에 Getter와 Setter를 자동 생성한다. 하지만 이것이 반드시 좋은 설계는 아니다. Getter는 데이터를 조회하기 위한 통로가 될 수 있지만, Setter는 객체 상태를 언제든 변경할 수 있게 만들기 때문이다.

예를 들어 다음과 같은 코드는 캡슐화가 약한 설계라고 볼 수 있다.
``` java
member.setAge(10); 
member.setAge(20);
member.setAge(30); 
```

객체 상태가 어디서 어떻게 변경되는지 추적하기 어려워진다.

반면 객체가 스스로 행동하도록 만들면 의미가 더욱 명확해진다.
``` java
order.startDelivery(); 
```
``` java
order.completeDelivery(); 
```

이처럼 단순히 값을 변경하는 것이 아니라 객체가 자신의 상태를 관리하도록 만드는 것이 객체지향적인 설계이다.

실무에서는 캡슐화를 강화하기 위해 Setter를 최소화하고 불변 객체(Immutable Object)를 사용하는 경우도 많다. 불변 객체는 생성 이후 상태가 변경되지 않는 객체를 의미한다. 상태가 변하지 않기 때문에 예측 가능성이 높고 멀티스레드 환경에서도 안전하게 사용할 수 있다.

Spring Framework 역시 캡슐화를 중요하게 생각한다. 서비스 계층은 자신의 비즈니스 로직을 내부에 숨기고, 외부에서는 공개된 메서드만 사용할 수 있도록 설계한다. 즉, 현대 Java 애플리케이션의 대부분은 캡슐화를 기반으로 만들어진다고 볼 수 있다.

결국 캡슐화는 단순히 필드를 private으로 선언하는 기술이 아니다. 객체 내부의 상태를 보호하고, 객체가 스스로 자신의 상태를 관리하도록 만드는 객체지향 설계 원칙이다. 이를 통해 데이터 무결성을 보장하고, 유지보수성을 높이며, 변화에 유연한 프로그램을 만들 수 있다. 따라서 캡슐화를 이해한다는 것은 단순한 문법을 배우는 것이 아니라 객체지향 프로그래밍의 핵심 철학을 이해하는 것과 같다고 할 수 있다.
