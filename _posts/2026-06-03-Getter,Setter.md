Java를 처음 공부할 때 가장 먼저 접하는 객체지향 개념 중 하나가 Getter와 Setter이다. 많은 개발자들이 IDE의 자동 생성 기능을 이용하여 별다른 고민 없이 Getter와 Setter를 생성하지만, 실제로는 단순히 값을 조회하고 수정하기 위한 메서드 이상의 의미를 가지고 있다. Getter와 Setter를 제대로 이해하기 위해서는 먼저 객체지향 프로그래밍의 핵심 원칙인 캡슐화(Encapsulation)를 이해해야 한다.

객체지향 프로그래밍에서는 객체가 자신의 상태(State)와 행동(Behavior)을 함께 관리해야 한다. 만약 객체 내부의 데이터를 외부에서 자유롭게 수정할 수 있다면 객체는 자신의 상태를 보호할 수 없게 된다. 예를 들어 회원 정보를 저장하는 Member 클래스가 있다고 가정해 보자.
``` java
public class Member {
     public String name;
 } 
```


위와 같이 필드를 public으로 선언하면 외부에서 언제든지 값을 변경할 수 있다.
``` java
member.name = "";
member.name = null; 
```
이러한 방식은 매우 위험하다. 이름이 비어 있으면 안 된다는 규칙이 있더라도 이를 강제할 방법이 없기 때문이다. 결국 객체는 단순한 데이터 저장소가 되고 객체지향 설계의 장점을 잃어버리게 된다.

이 문제를 해결하기 위해 Java에서는 일반적으로 필드를 private으로 선언한다.
``` java
private String name; 
```
private으로 선언된 필드는 클래스 외부에서 직접 접근할 수 없다. 즉, 객체 내부의 데이터를 보호할 수 있게 된다. 하지만 데이터를 완전히 숨겨버리면 외부에서 값을 조회하거나 변경할 수 없기 때문에 Getter와 Setter가 필요해진다.

Getter는 객체 내부 데이터를 읽기 위한 메서드이다.
``` java
public String getName() {
     return name; } 
```

Getter를 사용하면 외부에서는 객체의 데이터를 조회할 수 있지만 직접 수정할 수는 없다. 또한 단순히 값을 반환하는 역할만 하는 것이 아니라, 필요하다면 특정 데이터를 가공하여 반환하거나 추가적인 로직을 수행할 수도 있다. 따라서 Getter는 단순한 필드 접근이 아니라 객체가 허용한 방식으로 데이터를 제공하는 창구라고 볼 수 있다.

반면 Setter는 객체 내부 데이터를 변경하기 위한 메서드이다.
``` java
public void setName(String name) {
     this.name = name; } 
```
Setter의 가장 큰 장점은 데이터 변경 과정에서 검증 로직을 추가할 수 있다는 점이다.

``` java
public void setAge(int age) {
      if (age < 0) {
         throw new IllegalArgumentException();
     }
      this.age = age;
 } 
```
위 코드처럼 Setter 내부에서 잘못된 데이터를 차단할 수 있다. 만약 필드가 public이었다면 이러한 검증은 불가능했을 것이다. 즉, Setter는 단순히 값을 저장하는 메서드가 아니라 객체의 상태를 보호하는 역할도 수행한다.

하지만 여기서 많은 개발자들이 실수하는 부분이 있다. 바로 모든 필드에 무조건 Setter를 생성하는 것이다. Setter가 많아질수록 객체의 상태는 프로그램 어디에서든 변경될 수 있게 된다. 이는 객체가 자신의 상태를 통제하지 못하게 만들고 결국 캡슐화를 약화시키는 결과를 가져온다.

예를 들어 주문(Order) 객체가 있다고 가정해 보자.
``` java
order.setStatus("배송중");
order.setStatus("배송완료"); 
```


위 코드는 상태 변경이 자유롭기 때문에 객체가 어떤 흐름으로 동작하는지 파악하기 어렵다. 또한 잘못된 상태 변경도 발생할 수 있다.

실무에서는 이러한 문제를 해결하기 위해 Setter 대신 의미 있는 행동 메서드를 사용하는 경우가 많다.
``` java
order.startDelivery(); 
```
``` java
order.completeDelivery(); 
```

이러한 방식은 단순히 값을 변경하는 것이 아니라 객체가 스스로 자신의 상태를 관리하도록 만든다. 또한 비즈니스 로직을 객체 내부에 유지할 수 있기 때문에 유지보수성이 크게 향상된다.

최근에는 불변 객체(Immutable Object)를 사용하는 설계도 많이 사용된다. 불변 객체는 생성 이후 상태가 변경되지 않는 객체를 의미한다. 이러한 객체는 Setter 자체를 제공하지 않는다.
``` java
private final String name; 
```
생성자를 통해 값을 설정한 이후에는 변경할 수 없기 때문에 객체 상태를 더욱 안전하게 관리할 수 있다. 실제로 String 클래스 역시 대표적인 불변 객체이다.

Lombok을 사용하는 프로젝트에서는 @Getter와 @Setter 어노테이션을 자주 볼 수 있다. Lombok은 반복적인 코드를 자동 생성해 주어 생산성을 높여주지만, 편리하다는 이유만으로 모든 필드에 @Setter를 붙이는 것은 좋은 설계가 아니다. 실무에서는 Getter는 자주 사용하지만 Setter는 필요한 경우에만 제한적으로 사용하는 경우가 많다.

정리하면 Getter와 Setter는 단순히 필드에 접근하기 위한 메서드가 아니다. Getter는 객체의 데이터를 안전하게 조회하기 위한 통로이며, Setter는 객체의 상태를 통제하면서 변경하기 위한 창구이다. 이들의 궁극적인 목적은 캡슐화를 구현하여 객체가 자신의 상태를 스스로 관리하도록 만드는 것이다. 따라서 개발자는 Getter와 Setter를 자동 생성하기 전에 "정말 외부에서 조회가 필요한가?", "정말 외부에서 변경이 필요한가?"를 먼저 고민해야 한다. 이러한 고민이 좋은 객체지향 설계의 출발점이라고 할 수 있다.
